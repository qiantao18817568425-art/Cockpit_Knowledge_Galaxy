新人先看：60 秒理解结论

车里听到的“噪声”，实际是一段正常提示音被快速、反复地重新触发。音频系统不是无缘无故发声；每一次声音都能在日志中找到由 com.mb.core 主动创建并播放的记录。

正常情况

驾驶模式真的改变一次，系统识别到“旧模式 ≠ 新模式”，只播放一次约 3 秒的提示音。

本次异常

11:11:06—11:11:09，Android 接收链路把驾驶模式反复送成 0→1。其中 0 被映射成无效值 -1，随后每次回到 1 都再次被判断为“模式变化”，于是重新播放。

为什么抓包看起来“没有跳变”

项目同时存在两路来源：ICC CAN 持续发 1，DKCAN 持续发 0。每一路单独看都稳定、都没有跳变；但两路值彼此冲突。MCU 没有按来源仲裁和过滤，合并上报后才表现成 0→1→0→1。

谁需要优先处理

首要责任方向是 MCU/CAN 信号集成：明确该信号的唯一权威来源或来源优先级，并在 MCU 上报前完成过滤、去重。核心服务还应增加无效值隔离和重复播音保护；音频 HAL 不是根因。

“没有跳变”描述的是每一路自身稳定；异响来自两路稳定但互相冲突的值被 MCU 交替送到上层。这里必须区分四个观察点：

DKCAN项目侧确认该信号持续发 0，本身也没有跳变。DKCAN 单路数据稳定，但与 ICC CAN 冲突。不能作为驾驶模式的有效最终值直接覆盖权威来源。
MCU/上报链路项目侧确认 MCU 没有进行来源仲裁、过滤和去重。两路冲突值会被继续送往 canservice/Android。具体修改函数仍应在问题单中记录。
canservice → Android IPC日志在 11:11:06.149—11:11:09.589 明确记录 16 组 0→1。证明双源冲突最终确实转化成上层可见的交替值。日志本身不包含“ICC”与“DKCAN”来源标签；来源归属采用项目侧确认。

修复建议

优先级位置建议目的
P0CAN 信号矩阵/系统设计为 0x66002000 明确唯一权威来源或严格的来源优先级。若规范规定 ICC CAN 为权威源，则 DKC CAN 的 0 不得覆盖 ICC CAN 的 1；若存在切换条件，必须定义切换状态机。从设计上消除双源冲突。
P0MCU 上报逻辑增加来源仲裁、值有效性校验、最后有效值保持和去重；只有“权威来源的合法值真正变化”才允许上报。禁止把两路冲突值轮流透传。阻断 0/1 交替进入上层。
P0canservice IPC记录 sourceId/channelId，并对相同 Property 的冲突来源打印告警；必要时再次执行防抖和重复值抑制。提供第二道防线并提高可诊断性。
P1DrivingFeaturetoCommon=-1 视为无效输入，不更新“最后有效驾驶模式”，也不触发 modeChanged；仅当新旧两个值都合法且确实不同才播音。建立业务安全网。
P1提示音播放器相同提示音已经播放时，对短时间内的重复请求做合并或拒绝重启；阈值应由产品/音频规范确认，不应代替上游修复。降低异常信号对用户的可感知影响。
P2诊断日志为每次 modeChanged 打印 oldValidMode、rawValue、mappedValue、source、sequence/timestamp 和 playReason。下次可在一次抓日志中定位具体源。

闭环验证标准

  1. 双源冲突注入：保持 ICC CAN=1、DKCAN=0 至少 10 分钟，MCU 必须按信号矩阵输出唯一权威值，canservice IPC、VehicleClient 与 DrivingFeature 不得再出现 0/1 交替。
  2. 真实切换验证：人工执行 1→2、2→1 等合法切换，各层值一致，每次真实变化只触发 1 次提示音。
  3. 异常注入验证：向核心服务注入 1→无效0→1，预期无效值被丢弃，最后有效状态仍为 1，提示音播放次数为 0。
  4. 重复值验证：连续 100 次上报相同合法值，modeChanged[true] 和 play 均为 0 次。
  5. 多信号快照验证：同时监控车窗、门锁、儿童锁、灯光与驾驶模式，确认不再出现整组默认值/实际值交替。
  6. 音频回归：合法切换的提示音仍能完整播放；无焦点泄漏、无并发轨道堆积、无异常重启。
  7. 来源可观测性：MCU/canservice 日志应能区分 ICC CAN 与 DKCAN，并在来源冲突时打印仲裁结果，避免再次只能从交替值反推。
  8. 判退条件：只要权威源保持 1 时 canipc 仍出现 0x66002000=0 插入，或相同驾驶模式重复播音，即视为未闭环。

最终详细总结

1. 问题是什么

在用户指定的 11:09:00—11:11:20 范围内，11:11:06—11:11:12 出现最明显异常：一段约 3 秒的系统提示音被短间隔反复重启，形成“偶发噪声/异响”的听感。

2. 谁在发声

发声者明确为系统包 com.mb.core 的 AudioTrackPlayer，用途为驾驶辅助提示音。音频焦点已授权，AudioTrack 确实启动并向硬件交付音频帧。

3. 为什么反复发声

驾驶模式原始 ID 0x66002000 在输入链路中反复出现 0 和 1。0 被映射为无效模式 -1，1 被映射为有效模式 1；无效值进入状态后，每次恢复为 1 都再次满足“模式变化”，因此重新播音。

4. 与“CAN 没跳变”是否矛盾

不矛盾。ICC CAN 一直为 1，DKCAN 一直为 0，两路各自都没跳；但值彼此冲突。MCU 未过滤就上报，才在合并后的上层序列中形成 0/1 交替。

5. 当前根因定到哪一层

系统级根因已确认：同一驾驶模式信号存在双 CAN 来源冲突，MCU 缺少权威源仲裁、有效性过滤和重复值抑制。日志同时闭环了它如何继续触发 DrivingFeature 与提示音。

6. 为什么不是音频 HAL 首责

即使日志里有音频告警，也无法解释业务层为何恰好发出 16 次 play。播放请求与信号 0→1 逐次对应，说明音频链路主要是在执行上层明确下发的动作。

7. 应该怎样修

在信号矩阵中明确唯一权威源或严格优先级，MCU 只允许权威来源的合法变化向上报告；同时在 canservice 和核心服务增加冲突告警、无效值隔离、去重及重复播音保护。

8. 怎样证明修好了

在 ICC=1、DKCAN=0 的冲突注入条件下，上层只能得到一个按规范仲裁后的稳定值；真实模式变化只播放一次，无效值和重复值均不得触发提示音。

最终判定：根因已经在系统链路层闭环：ICC CAN=1 与 DKCAN=0 双源冲突，MCU 未过滤/仲裁即上报，导致上层 0/1 交替并连续触发提示音。剩余工作属于修复实施与回归验证，不再是根因猜测。
