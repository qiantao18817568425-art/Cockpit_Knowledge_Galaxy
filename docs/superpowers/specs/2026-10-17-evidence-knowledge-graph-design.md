# 座舱知识银河：证据型知识图谱设计规格

日期：2026-10-17  
状态：设计已口头确认，等待书面规格复核  
目标站点：`https://qiantao18817568425-art.github.io/Cockpit_Knowledge_Galaxy/`

## 1. 背景

当前站点已经具备 Obsidian 风格的 3D 银河、悬停放大、点击聚焦、搜索、章节课程索引和原始资料下载，但知识层仍以目录索引为主。

当前图谱包含 152 个节点、399 条关系。299 份公开原始资料只形成 15 个资料分类节点；关系类型只有主题目录、主题归类、主题细分、内容索引和课程顺序。现有流程已经索引大量正文，但尚未把正文转化为组件、接口、状态、流程、观测点及逐页证据。

本设计把站点从“资料目录图”升级为“证据型知识图谱”。图谱中的技术结论必须能够回到资料、版本和页码，并明确其适用范围和证据状态。

## 2. 目标

1. 对已公开的 299 份去重资料建立完整处理状态，覆盖顶层文件及压缩包内可读文档。
2. 从资料中提炼可复用的座舱知识实体和有方向、有语义的关系。
3. 分开控制路径、数据路径和电源路径，显示 Android Guest、Yocto Host、MCU、TBox 与 Hypervisor 边界。
4. 所有公开技术结论至少关联一处来源证据，包含文档、版本和页码或章节。
5. 保留 MT8668、MT8676、T12T、PVT、参考平台和现车配置之间的差异，不把历史资料直接写成现车事实。
6. 保持现有 3D 银河体验：空闲旋转、悬停文字放大、点击聚焦、搜索和详情面板。
7. 默认视图保持清晰；原始文档节点按需展开，不让 299 份文件同时挤占主视图。

## 3. 不在本次范围内

- 不把相同名称的状态码、GPIO、IRQ、VMID、超时或错误码跨版本固化。
- 不根据单一关键词自动发布技术结论。
- 不把课程发布状态解释为学习完成度或实车验证状态。
- 不在主视图默认展开全部原始文件和全部页级证据。

## 4. 当前资料覆盖基线

本地资料库当前记录 301 份唯一内容，其中 2 项不进入公开知识库：一个系统缓存文件和一个 0 字节 PDF。公开目录为 299 份。

- 284 份顶层文档已建立正文索引。
- 共索引 5,555 页，约 766 万字符。
- 15 个压缩包已建立成员目录。
- 压缩包内 49 份 PDF、Office 或文本资料已经展开；43 份具有可搜索正文，共 475 个可搜索页或章节；6 份未能提取文字。
- 图片页、扫描页和无法提取文字的文档保留“需视觉复核”状态。

资料处理完成度与知识吸收完成度必须分开统计。

## 5. 推荐方案

采用“知识实体为主、原始资料为证据”的图谱。

主视图展示领域、运行域、组件、接口、状态、流程和观测点。原始资料作为证据层，在点击知识点或开启“显示证据”时展开。这样既能保持关系图可读，又能证明每个结论来自哪里。

文档中心方案会造成主图拥挤；纯手工模块树无法稳定追踪页码和版本，因此不采用。

## 6. 图谱分层

### 6.1 一级入口

- 座舱知识
- 平台与版本
- 运行域
- 功能域
- 业务流程
- 诊断与证据
- 原始资料
- 架构课程

### 6.2 运行域

- MCU / AUTOSAR
- SoC / Hypervisor
- Yocto SOS Host
- Android AAOS Guest
- TBox Linux 或融合业务
- 物理设备与外设

运行域节点用于表达组件部署位置和跨域边界，不直接代表当前车型一定采用该部署。

### 6.3 功能域

沿用并细化现有领域：平台、虚拟化、Android、Yocto、MCU、TBox、显示、触控、Camera/AVM、音频、网络、电源、启动、稳定性、性能、USB/存储、安全/TEE、跨域通信、诊断与日志。

### 6.4 知识实体类型

| 类型 | 含义 | 示例 |
|---|---|---|
| `platform` | SoC、车型或硬件阶段 | MT8668、MT8676、PVT |
| `domain` | 运行域或功能域 | Android Guest、电源管理 |
| `component` | 硬件、服务或软件组件 | SleepManager、PMIC、SurfaceFlinger |
| `interface` | 跨组件接口或协议 | SPI、IPCL、Vsock、Binder |
| `state` | 有版本范围的状态 | STR、Running、Suspend Transition |
| `process` | 可展开的业务流程 | 休眠进入、Resume、Camera 首帧 |
| `observation` | 日志、计数器、寄存器或测点 | wakeup_sources、first frame、carrier |
| `failure_mode` | 证据边界明确的失效模式 | noirq abort、virtqueue 无回调 |
| `source` | 原始资料或课程 | PDF、PPTX、架构章节 |
| `evidence` | 来源中的页级证据 | 文档第 4 页的流程说明 |

## 7. 关系模型

每条边必须有方向和类型。

| 关系 | 含义 |
|---|---|
| `belongs_to` | 属于某运行域或功能域 |
| `runs_on` | 组件运行于某 OS 或 VM |
| `controls` | 控制命令、策略或状态驱动 |
| `sends_to` | 消息或请求发送方向 |
| `publishes` / `subscribes` | 发布订阅关系 |
| `carries_data_to` | 帧、PCM、网络包或 buffer 数据路径 |
| `powers` | 供电和电源域关系 |
| `transitions_to` | 状态迁移 |
| `depends_on` | 启动、生命周期或资源依赖 |
| `observed_by` | 可验证该节点的观测点 |
| `fails_as` | 组件或接口可能表现出的失效模式 |
| `supported_by` | 知识结论的证据来源 |
| `variant_of` | 平台、版本或语言版本关系 |
| `conflicts_with` | 不同资料间存在冲突或定义差异 |
| `supersedes` | 新版资料替代旧版资料 |

控制、数据和电源关系使用不同颜色与图例。推断关系使用虚线；已由当前版本确认的关系使用实线。

## 8. 证据与版本规则

### 8.1 知识陈述

每项可发布知识以独立陈述保存，至少包含：

- 陈述内容
- 主体、关系和客体
- 平台、车型、硬件阶段、软件版本
- 来源文档 ID、文档版本、页码或章节
- 证据状态
- 提取与复核状态
- 适用范围及限制
- 最后复核日期

### 8.2 证据状态

- `confirmed_current`：由当前车型和版本资料确认。
- `documented_reference`：资料中明确描述，但尚未确认适用于当前车辆。
- `inferred_mapping`：根据上下文映射出的候选关系，等待复核。
- `conflicting`：资料之间存在不一致。
- `needs_visual_review`：依赖图片、表格或扫描页，正文提取不足。

页面不得把后三种状态显示成已经确认的现车事实。

### 8.3 版本处理

- 同一手册 V1.0、V1.1、V1.2、V1.3 建立 `supersedes` 关系。
- 中英文版本可归到同一知识实体，但保留两个来源节点。
- MT8668 和 MT8676 默认分开；只有资料明确说明共用时才建立共享关系。
- 当前车型、SoC、硬件阶段或构建号未知时，必须显示“适用版本待确认”。

## 9. 电源管理首个验收样板

电源管理作为数据模型和交互的第一块完整样板，至少覆盖：

1. ACC、IG、CAN、RTC、Modem 等输入和唤醒源。
2. MCU PowerManager、电源模式决策、超时、心跳和复位策略。
3. GPIO、SPI、IPCL 等跨域控制和状态回读。
4. Yocto SleepManager、Android、TBox 和 Hypervisor 休眠屏障。
5. Kernel suspend、ATF、SPM、DRAM 自刷新、VCORE 和 PMIC。
6. MT6363 电源树、Buck、LDO、上电关机时序、复位、看门狗、热关断、SPMI 和 AUXADC。
7. 主电、备电、TBox 保活和 Modem/RTC 唤醒。
8. 软件 wake 请求、休眠进入失败、稳定睡眠后唤醒三种事件。
9. WakeLock、device callback、noirq、clkchk、CRTC/PLL/SMI 和 wake source 等观测点。
10. MT8668、MT8676 以及 Android、Yocto、Hypervisor 手册之间的版本差异。

样板通过验收后，同一模式覆盖其余领域，不重新设计数据结构。

## 10. 资料吸收流程

### 10.1 登记与提取

1. 校验 299 份公开资料的 SHA-256、文件名、格式和下载链接。
2. 读取顶层 PDF、PPTX、DOCX、XLSX 和文本。
3. 对压缩包保留容器节点，并读取已经展开的可读成员。
4. 对图片页或无文字页建立视觉复核任务。

### 10.2 候选知识生成

从标题、目录、正文、表格和图注中识别平台、运行域、组件、接口、状态、流程、观测点、版本和页面引用。候选知识不会直接发布。

### 10.3 规范化与去重

- 合并同义词和中英文名称。
- 保留原名、规范名和搜索别名。
- 合并相同知识实体，保留多个证据来源。
- 将版本更新、冲突和平台差异建成关系。

### 10.4 证据复核

逐条核对候选知识与原始页，检查：

- 主体、关系、客体是否由原文支持。
- 页码与文档版本是否正确。
- 资料描述的是参考设计、平台能力还是当前项目事实。
- 控制、数据和电源路径是否混淆。
- 常量、状态码和阈值是否被错误跨版本复用。

只有通过复核的陈述进入默认知识图；待核陈述进入可选的“候选关系”层。

## 11. 页面交互

### 11.1 默认状态

- “座舱知识”位于中心。
- 无搜索、无选择并空闲一段时间后缓慢 3D 旋转。
- 默认展示一级领域、主要运行域和少量高价值组件。

### 11.2 点击节点

- 点击领域或组件后，将该节点平滑移至视图中心。
- 显示一跳关系，必要时允许展开到两跳。
- 原始资料不会自动全部展开；用户点击“证据”后才出现来源节点。
- 点击空白或主页按钮返回总览。

### 11.3 悬停节点

- 节点及标题平滑放大。
- 显示实体类型、简短说明、直接关系数和证据数。
- 鼠标移开后恢复原大小。

### 11.4 详情面板

详情面板显示：

- 定义与职责
- 所在运行域和适用平台
- 上游、下游及关系类型
- 控制、数据和电源路径
- 正常状态或流程
- 诊断观测点和证据边界
- 来源资料、版本、页码及下载链接
- 已确认、参考、推断、冲突或待视觉复核状态

### 11.5 搜索与过滤

- 搜索规范名、别名、服务名、协议名、状态和原始文档。
- 支持 MT8668、MT8676、运行域、功能域、关系类型和证据状态过滤。
- 搜索结果优先显示知识实体，再显示原始资料。

## 12. 数据文件设计

建议拆分为：

- `content/entities.json`：规范知识实体。
- `content/relations.json`：有类型的关系。
- `content/claims.json`：知识陈述及版本范围。
- `content/evidence.json`：来源、页码和证据状态。
- `content/source-register.json`：299 份资料及压缩包成员处理状态。
- `docs/graph.json`：供前端读取的发布产物。

构建脚本负责校验引用完整性、生成聚合统计并输出前端数据。原始本机路径不得进入公开文件。

## 13. 错误处理

- 缺失来源、页码或实体引用时构建失败。
- 下载链接失效时构建失败或阻止发布。
- 关系引用不存在的节点时构建失败。
- 无法提取文字的资料保留状态，不生成无证据技术结论。
- 不同版本冲突时同时保留，不自动选择一方。
- 前端加载失败时显示明确错误和可访问的资料目录链接。

## 14. 验收标准

### 14.1 全量资料

- 299 份公开资料全部具有处理状态、分类、版本线索和下载链接。
- 压缩包内所有可读 PDF、Office 和文本成员均具有提取状态。
- 无文字资料具有视觉复核状态。

### 14.2 知识质量

- 默认知识节点均至少有一条 `supported_by` 证据关系。
- 证据包含文档和页码或章节。
- MT8668 与 MT8676 的平台差异可过滤和识别。
- 参考架构、当前项目事实和推断关系在视觉上可区分。
- 控制、数据和电源路径可分别查看。

### 14.3 交互

- 空闲旋转、拖动、缩放、悬停放大、点击聚焦和返回总览正常。
- 搜索能够命中规范名、别名和资料名。
- 详情面板能够打开原始资料及对应证据。
- 节点较多时仍可通过分层加载维持可读性和交互性能。

### 14.4 工程验证

- 构图测试覆盖节点唯一性、关系合法性、证据完整性、版本字段和公开链接。
- 现有章节、课程和原始资料链接继续可用。
- GitHub Pages 发布后验证首页、图谱数据、原始资料页和抽样证据链接。

## 15. 实施阶段

1. 建立新数据模式和校验器。
2. 完成电源管理全链样板并更新前端交互。
3. 复核样板的证据、版本、路径和页面可读性。
4. 按领域批量吸收其余资料。
5. 处理跨领域实体、重复、版本更新和冲突。
6. 完成全量测试、GitHub 更新和 Pages 验证。

## 16. T12T 技能约束

本设计使用用户指定的 F 盘 T12T 优化版 21 项技能完成覆盖检查。平台架构、电源与 STR、跨域通信、MCU、虚拟化和启动 HMI 用于首个样板的深入建模；显示、触控、Camera、音频、稳定性、性能、网络、USB、TEE、DB/KE 和日志专项用于规定其领域边界与观测点；TPM 两项用于处理证据状态、责任边界、验证和闭环字段。

技能中的历史案例、数值和候选拓扑只作为参考。最终公开知识以原始资料、当前版本和实际项目定义为准。
