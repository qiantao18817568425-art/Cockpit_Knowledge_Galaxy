新人先看：60 秒读懂这个问题

先不看 CAN 编号、进程号和音频参数。把问题理解成一句话：车机本来只需要完整播放一次提示音， 但它误以为驾驶模式在不停切换，于是同一段提示音刚响一点就被停止，然后又从头播放；连续重复后，乘员听到的就不再像正常提示音，而像来源不明的“滴滴声”或异常噪声。

① 车辆报告状态车内通信系统告诉车机当前驾驶模式
→
② 状态来回跳变日志中模式 0 和 1 在很短时间内反复出现
→
③ 应用重复播放每收到一次模式 1，就重新播放同一提示音
→
④ 听起来像噪声3 秒声音多数只响约 0.1 秒，就被下一次播放打断

正常情况应该怎样

驾驶模式真正发生一次变化，车机识别到一次有效变化，提示音播放一次，并完整播放结束。重复上报相同状态时，不应再次播放。

实际发生了什么

驾驶模式值在 0 和 1 之间快速往返。应用把每次值 1 都当成一次新的模式变化，累计发起 92 次播放。

为什么会听成“噪声”

声音本身不一定损坏；问题是它被切成许多很短的开头。89 次播放在半秒内被停止，最常见的实际时长只有约 0.085 秒或 0.128 秒。

应该由谁处理

CAN/VHAL 团队需要查清状态为什么跳变和映射为什么失败；com.mb.core 团队需要增加有效值过滤、防抖和播放去重。两侧都属于最高优先级。

目前还不知道 Android 日志只能证明“车机收到的值在跳”，不能单独证明是 MCU、网关、真实 CAN 总线还是 Android 转换层最先制造了抖动；还需要同一时间段的原始 CAN trace。附件也不是座舱录音，因此声音听感仍需要录音对时确认。
建议阅读路线：第一次接触问题时，先看本节和下面的名词解释；需要理解原因时看第 1～5 节；需要复核证据时看第 6 节；开发、测试和问题经理可重点看第 7～12 节。

先认识 5 个名词

车辆信号（CAN）可以理解为车内各控制器之间传递状态的“消息”。这里传递的是驾驶模式等车辆状态。
Android 车辆翻译层（VHAL）把车辆原始信号转换成 Android 应用能理解的属性，相当于车辆与应用之间的翻译员。
业务应用（com.mb.core）根据车辆状态执行功能。本问题中，它判断驾驶模式是否变化，并决定是否播放提示音。
播放器（AudioTrack）Android 真正把声音数据送到音频系统的播放对象。每次重建或停止都会改变实际听到的声音。
音频帧（frames）衡量实际播放了多少声音数据。48 kHz 下，144000 帧是 3 秒；4100 帧只有约 0.085 秒。

根因结论

异常声音由 com.mb.core（PID 4509） 的 AudioTrackPlayer 发起，属于 USAGE_ASSISTANCE_SONIFICATION 系统提示音。单个音频为 48 kHz、双声道、16 bit PCM， 数据长度 576000 bytes，对应 3 秒。故障期间，驾驶模式原始信号 0x66002000 在 0 ↔ 1 间约每 100 ms 反复切换；模式 0 被跳过，模式 1 每次都触发新的播放请求。 因而同一提示音被请求 92 次，其中 89 次在 0.5 秒内被下一次请求打断，形成连续短促、重复的异常提示音听感。

直接证据 CAN 值 0/1 各 92 次；DrivingFeature 模式 0/1 各 92 次；AudioTrackPlayer.play() 92 次，计数严格对应。
分析推断 用户听到的“偶发噪声”高度疑似就是被反复截断的系统提示音；但附件是 logcat 文本而非座舱录音，具体声纹仍需录音与日志时间对齐确认。

9修复优先级

优先级措施责任域验收结果
P0核对 0x66002000 → 0x21406002 的 DBC/枚举/conversion；未命中值禁止直接作为有效模式透传。CAN / VHAL / VehicleConnector0、1 均有明确合法映射；无效值保持 last-known-good 或标记 INVALID。
P0追查 20～100 ms 的 0/1 抖动：检查重复 source、周期帧/事件帧竞争、网关转发与上电默认值。MCU / 网关 / 整车信号真实模式不变时，Android property 不再往返变化。

12最终详细总结（用于问题单与评审会）

通俗版结论 这不是“喇叭自己突然产生了声音”。车机收到的驾驶模式状态在短时间内不停地变成 0、又变成 1； 应用每看到一次 1，就让同一段提示音重新从头播放。新声音开始前，旧声音会被停止，所以原本应该持续 3 秒的提示音， 大多数只响了约十分之一秒。许多声音开头连续出现，最终就被乘员感知为间歇性的异常噪声。

问题现象与最终判定

日志在 19:33:59～19:36:58 之间记录到三段成组出现的系统提示音播放。三段分别包含 68、19、5 次请求， 合计 92 次。每个请求的源音频理论长度为 3 秒，但其中 89 次只交付 4100～20484 帧，即约 0.085～0.427 秒， 随后就被新的播放请求停止。最终判定为：用户所描述的间歇性异常噪声，高度疑似是同一系统提示音在短周期内反复起播、 被打断后形成的密集短音，而不是普通媒体声、持续性底噪或已观察到的 DSP 崩溃。

已闭环的直接失效机制

  • VehicleClient 收到驾驶模式 CAN libid 0x66002000 的值 0 和 1，各 92 次。
  • VehicleConnector 对两个值均提示 conversion 未找到对应 canValue，但仍将原值继续上传。
  • DrivingFeature 将值 0 转换为 toCommon=-1 并跳过播放；将值 1 转换为模式 1，并判定 modeChanged=true。
  • 每次模式 1 都调用同一个 AudioTrackPlayer.play()，总计恰好 92 次。
  • 下一次请求进入时执行 stopInternal；89 条旧 AudioTrack 在未播完时被停止，仅三个窗口的最后一轨完整交付 144000 帧。

根因分层与责任边界

  • 直接触发源：DRIVING_MODE 在 0/1 之间短周期抖动。这一层有严格的事件计数和毫秒级时序证据。
  • 直接失效点：com.mb.core 对车辆模式输入缺少稳定态过滤，并在相同提示音已经播放时继续 stop/recreate，放大了上游抖动。
  • 明确配置问题：0x66002000 的 conversion 对 0 和 1 均未命中；枚举定义、合法值或映射配置至少有一项需要修正。
  • 上游根源待验证：当前 Android 日志不能区分 MCU/网关真实发送抖动、多个 source 竞争、上电默认帧覆盖，还是 VHAL 转换/批处理错误。
  • Audio HAL 次要问题：gain fallback、Headset mixer 缺失和 htimestamp 失败会影响音频路径质量，但没有证据表明它们产生了本次播放触发。

影响与风险评估

  • 用户体验：3 秒提示音被切成约 0.1 秒的碎片反复起播，容易被感知为“滴滴滴”、爆裂感或来源不明的异常噪音。
  • 功能风险：多路车辆属性在相同时间窗同步变化，说明风险可能不仅限于声音；若业务层对这些值直接响应，可能产生界面或车控状态抖动。
  • 复现风险：问题仅在三个短窗口出现，常规静态 AudioFlinger dump 很容易错过，必须使用统一时钟做 CAN→VHAL→业务→AudioTrack 的连续采集。
  • 误判风险：若只看 Audio HAL 告警，容易把问题归因到扬声器或 DSP；现有时序显示 HAL 告警跟随播放请求出现，而不是先于播放触发。

责任域与建议动作

  • CAN/VHAL P0：核对 DBC 与 property conversion，抓取同窗原始 CAN trace，确定抖动究竟来自源端还是 Android 转换链。
  • com.mb.core P0：以最后一个合法稳定模式判断变化，忽略无效态；增加 300～500 ms 或连续 N 帧稳定判定。
  • AudioTrackPlayer P1：相同提示音播放中去重，设置重触发抑制窗口，不再对相同请求无条件停止并重建。
  • Audio HAL P2：分别处理 bus gain device 映射、错误 mixer control 和 htimestamp 告警，避免其加重切换听感。

问题关闭标准

  • 真实驾驶模式保持不变时，Android DRIVING_MODE 不再出现 0/1 往返变化。
  • 一次合法模式切换只产生一次提示音播放；重复 property 上报不产生新的 play。
  • 人工注入快速 0/1 抖动时，应用能过滤无效输入且不连续重启 AudioTrack。
  • 连续 10 分钟台架或道路测试中不再出现约 100 ms 周期的播放/停止序列。
  • 座舱录音与日志统一时间对齐，确认现场异常声音消失，同时正常模式切换提示音仍可完整播放。
最终一句话结论： 本问题的直接失效链已经由日志闭环——驾驶模式信号 0x66002000 以约 100 ms 周期在 0/1 间抖动， conversion 未命中后仍被透传，com.mb.core 又缺少稳定态过滤和相同提示音播放去重，最终造成一段 3 秒系统提示音被请求 92 次， 其中 89 次在 0.5 秒内被打断；当前应由 CAN/VHAL 与 com.mb.core 共同作为 P0 修复责任域，Audio HAL 告警另行清理， 而导致上游信号抖动的具体源端仍需 MCU/网关原始 CAN trace 才能最终闭环。
